# 업체 관리 대시보드 운영 안정화 및 UX 전면 개선 설계

## 1. 목적

업체 관리 대시보드를 실제 팀 운영에 견딜 수 있는 수준으로 개선한다. 직원이 처음 접속해도 현재 상황과 다음 행동을 이해할 수 있어야 하며, 저장·전환·중복 입력·느린 네트워크·공용 기기·공개 고객 링크에서 데이터 유실이나 권한 오용이 발생하지 않아야 한다.

이번 개선은 기존 Redis 데이터와 고객에게 발급된 계약서·안내문·리포트 링크를 보존한다. 데모는 임시로 운영 사이트에 유지하되 운영 데이터 및 운영 API와의 경계를 코드와 테스트 양쪽에서 강제한다.

## 2. 기본 원칙

- 기존 Redis 키와 저장 문서는 호환성을 유지한다.
- 데이터 삭제, 키 이름 일괄 변경, 고객 링크 재발급은 하지 않는다.
- 변경은 안정성, 핵심 업무 흐름, 시각 체계, 코드 구조 순으로 나누어 배포한다.
- 각 단계는 이전 단계로 되돌릴 수 있는 독립 커밋과 배포 단위로 구성한다.
- 색상, 모션, 장식보다 업무 판단과 오류 예방을 우선한다.
- 데스크톱, 태블릿, 390px 모바일에서 핵심 기능을 동일하게 사용할 수 있어야 한다.
- 모션 줄이기 환경에서는 공간 이동을 제거하고 상태 정보는 유지한다.

## 3. 현재 구조와 핵심 위험

현재 애플리케이션은 약 30만 자 규모의 단일 `index.html`에 화면, 상태, 저장소, API 호출, 모션 로직이 결합되어 있다. 서버 측은 Vercel Functions와 Upstash Redis를 사용하며, 네이버 검색광고 및 데이터랩 API를 프록시한다.

주요 위험은 다음과 같다.

1. 팀 비밀번호 원문이 인증 토큰으로 재사용되고 브라우저 `localStorage`에 저장된다.
2. 인증·데모·고객 공개 화면이 같은 문서와 전역 상태를 공유한다.
3. 여러 저장 작업에 중복 제출 방지가 일관되게 적용되지 않는다.
4. 작성 중인 입력값이 렌더링이나 탭 전환으로 사라질 가능성이 있다.
5. 공개 리포트 식별자는 계약서·안내문보다 엔트로피가 낮다.
6. 로딩·빈 상태·오류·저장 완료 표현이 화면별로 다르다.
7. 테스트는 존재하지만 CI가 없어 오래된 단언이 운영 코드와 어긋나도 발견이 늦다.
8. 하나의 파일에서 작은 변경이 다른 기능에 회귀를 만들 가능성이 크다.

## 4. 단계별 개선 구조

### 4.1 1단계: 인증과 데이터 안정성

#### 인증

- `/api/auth`는 팀 비밀번호 원문을 응답하지 않는다.
- 로그인 성공 시 서버가 서명한 불투명 세션을 발급한다.
- 세션은 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키에 저장한다.
- 세션에는 발급 시각과 만료 시각을 포함하고 최대 유지 시간은 12시간으로 제한한다.
- 서버 API는 쿠키 세션을 검증하며, 마이그레이션 기간에만 기존 헤더 토큰을 제한적으로 허용한다.
- 로그아웃은 서버 세션 쿠키를 즉시 만료시킨다.
- 인증 실패는 IP 및 익명 클라이언트 기준으로 제한한다. 10분 동안 5회 실패 시 15분간 추가 시도를 차단한다.
- 오류 응답은 환경변수 이름이나 내부 저장소 구성을 노출하지 않는다.

#### 저장 안정성

- 저장 버튼은 요청이 끝날 때까지 비활성화하고 같은 문서의 중복 요청을 합친다.
- 계약서 제출, 안내문 제출, 재계약 처리에는 idempotency 키를 사용한다.
- 화면 이동 전에 편집 중인 초안을 동기화한다.
- 저장 실패 시 작성 내용을 유지하고 명시적인 재시도 버튼을 제공한다.
- 서버는 문자열 길이, 배열 개수, 데이터 URL 크기, 허용 필드를 검증한다.
- Redis 오류 메시지나 토큰은 클라이언트에 전달하지 않는다.

#### 공개 링크

- 새 리포트 ID는 `crypto.getRandomValues` 기반 24바이트 난수를 사용한다.
- 기존 리포트 ID는 계속 열 수 있어야 한다.
- 공개 계약서·안내문·리포트 응답은 허용 필드만 반환한다.
- 공개 쓰기 요청은 문서별 속도 제한과 요청 크기 제한을 적용한다.
- 향후 만료와 폐기를 추가할 수 있도록 `revokedAt`, `expiresAt`을 선택 필드로 허용한다.

### 4.2 2단계: 핵심 운영 흐름

#### 통합 첫 화면

첫 화면은 장식적인 통계보다 당일 판단을 우선한다.

- 상단 요약: 관리 중, 시작 예정, 재계약 필요, 저장 실패/주의 항목
- 오늘의 우선 업무: 마감 임박, 미완료, 고객 회신 대기
- 업체 현황: 상태, 담당자, 계약 회차, 진행일, 다음 행동
- 최근 활동: 마지막 저장·계약·리포트·안내문 변경

각 카드에는 수치뿐 아니라 클릭 후 무엇을 볼 수 있는지 짧은 안내를 제공한다.

#### 업체 등록과 수정

- 등록 과정을 기본 정보, 계약 정보, 운영 설정의 세 구역으로 나눈다.
- 필수값과 선택값을 명확히 구분한다.
- 업종은 요식업, 병·의원, 법률·전문서비스, 교육, 운동·건강, 뷰티, 소매, 기타로 제공하고 직접 입력을 허용한다.
- 저장 오류는 필드 가까이에 표시하고 첫 오류 필드로 이동한다.
- 작성 중 나가기를 누르면 변경사항이 있을 때만 확인한다.

#### 업체 상세

- 상단에는 업체명, 운영 상태, 담당자, 진행일, 계약 회차와 다음 행동을 배치한다.
- 달력, 체크리스트, 리포트, 계약서, 정보 안내문 탭은 동일한 선택 규칙을 사용한다.
- 탭 전환은 작성 중 내용을 먼저 메모리 상태에 반영한다.
- 각 탭은 빈 상태에서 생성 또는 입력 방법을 안내한다.

#### 달력과 체크리스트

- 날짜 선택 시 해당 날짜의 업무, 메모, 완료 상태를 한 패널에서 처리한다.
- 빠른 연속 클릭은 한 번의 상태 변경으로 처리한다.
- 체크리스트 재정렬·추가·삭제 후 초안이 즉시 보존된다.
- 주차와 마감 구간은 색상과 텍스트를 함께 사용한다.
- 완료율은 분모가 0일 때 0%와 안내 문구를 표시한다.

#### 계약서·안내문·리포트

- 내부 편집 화면과 고객 공개 화면을 시각적·논리적으로 분리한다.
- 고객이 제출을 완료한 뒤에도 명시적으로 허용된 필드만 수정할 수 있다.
- 서명·제출 직전에는 변경되는 상태를 요약한다.
- PDF 인쇄 화면에는 내부 메모와 관리 버튼이 포함되지 않는다.
- 리포트 공유 링크는 읽기 전용임을 화면에 표시한다.

#### 키워드 분석기

- 단일조회, 연관 키워드, 대량조회의 모드는 하나의 상태값으로 관리한다.
- 모드 전환 시 이전 입력과 결과를 초기화한다.
- 동시에 하나의 탭만 활성화한다.
- 요청 중 재검색을 막고 취소 또는 완료 후 다시 검색할 수 있게 한다.
- 네이버 API 실패, 사용량 제한, 빈 결과를 서로 다른 상태로 안내한다.
- 추정치는 실제 검색량이 아니라는 설명을 결과와 함께 유지한다.

## 5. 디자인 시스템

### 5.1 정보 계층

- 페이지 제목: 현재 업무 영역
- 보조 설명: 이 화면에서 할 수 있는 일
- 주요 행동: 화면당 하나의 파란색 기본 버튼
- 보조 행동: 회색 또는 텍스트 버튼
- 위험 행동: 빨간색과 확인 대화상자

카드 안에서 제목, 상태, 보조 정보, 행동의 순서를 통일한다. 동일한 역할의 요소는 화면마다 같은 크기와 위치를 사용한다.

### 5.2 상태 표현

- 파란색: 선택 및 진행
- 초록색: 완료 및 정상
- 주황색: 임박 및 확인 필요
- 빨간색: 실패 및 위험
- 회색: 대기 및 비활성

상태는 색상만 사용하지 않고 문구, 아이콘 또는 배지를 함께 제공한다. 활성 탭은 배경, 글자색, 테두리 중 하나의 일관된 조합만 사용한다.

### 5.3 반응형

- 920px 이상: 대시보드 요약과 업무 목록을 2열까지 허용한다.
- 600~919px: 주요 카드 2열, 상세 내용 1열
- 599px 이하: 모든 핵심 콘텐츠 1열, 터치 대상 최소 높이 44px
- 390px에서 가로 스크롤이 발생하지 않아야 한다.
- 표는 핵심 열을 카드형 행으로 전환하거나 내부 스크롤 영역임을 명시한다.
- 고정 버튼은 키보드와 모바일 브라우저 안전 영역을 가리지 않는다.

### 5.4 모션

- 누름 피드백: 110ms
- 상태 전환: 200ms
- 화면 공간 이동: 최대 460ms
- 저장 완료는 짧은 체크 피드백으로 표시한다.
- 반복 펄스와 지속 글로우는 긴급 상태 외에는 사용하지 않는다.
- 모션 줄이기 환경에서는 이동과 확대를 제거한다.

## 6. 데모 임시 유지 정책

- 데모 진입에는 인증이 필요하지 않다.
- 데모 상태는 운영 인증 상태를 읽거나 재사용할 수 없다.
- 데모 저장소는 `rs:browser-demo-workspace:v1` 네임스페이스만 사용한다.
- 데모 모드에서는 `/api/data`, `/api/auth`, `/api/guide`, 네이버 API 호출을 허용하지 않는다.
- 계약서·안내문·리포트의 외부 링크 발급을 허용하지 않는다.
- 데모 화면 전체에 지속적인 DEMO 표식을 표시한다.
- 자동화 테스트는 데모 모드에서 네트워크 호출이 0회임을 검증한다.
- 데모 로직은 별도 모듈 경계를 유지해 향후 별도 Vercel 프로젝트로 이동할 수 있어야 한다.

## 7. 코드 구조 개선

한 번에 프레임워크를 도입하거나 전체 파일을 재작성하지 않는다. 먼저 기존 동작을 테스트로 고정한 뒤 아래 순서로 분리한다.

- `src/auth.js`: 로그인, 로그아웃, 세션 상태
- `src/storage.js`: Redis API와 데모 저장소 어댑터
- `src/state.js`: 화면·탭·편집 초안 상태
- `src/ui/feedback.js`: 로딩, 토스트, 확인, 저장 상태
- `src/features/dashboard.js`
- `src/features/clients.js`
- `src/features/calendar.js`
- `src/features/checklists.js`
- `src/features/contracts.js`
- `src/features/guides.js`
- `src/features/reports.js`
- `src/features/keywords.js`

`index.html`은 공통 스타일과 애플리케이션 진입만 담당하도록 점진적으로 축소한다. 각 단계에서 기존 전역 함수를 호환 래퍼로 유지해 한 번에 모든 기능이 깨지지 않게 한다.

## 8. 오류 처리

모든 비동기 화면은 다음 네 상태를 명시적으로 가진다.

1. idle: 아직 요청하지 않음
2. loading: 요청 중이며 중복 행동 차단
3. success 또는 empty: 정상 결과 또는 정상적인 빈 결과
4. error: 작성 내용 유지, 오류 설명과 재시도 제공

네트워크 오류와 인증 만료를 구분한다. 인증 만료는 저장 중인 초안을 보존한 뒤 로그인 화면으로 이동하고, 재로그인 후 복구할 수 있어야 한다.

## 9. 테스트와 배포

### 자동 테스트

- 인증: 성공, 실패, 만료, 변조, 속도 제한, 로그아웃
- 저장: 중복 클릭, 동일 요청 재전송, Redis 실패, 잘못된 저장 문서
- 편집: 탭 전환, 뒤로가기, 새로고침 전 초안 보존
- 공개 링크: 인증 없는 허용 읽기, 비허용 필드 차단, 폐기·만료
- 데모: 운영 API 호출 0회, 네임스페이스 격리
- 반응형: 390px, 600px, 920px 가로 넘침
- 접근성: 키보드 포커스, 레이블, 대화상자 포커스 복귀, 모션 줄이기
- 핵심 흐름: 로그인 → 업체 등록 → 업무 완료 → 리포트 → 계약서·안내문

### CI 및 배포

- GitHub Actions에서 전체 Node 테스트와 인라인 스크립트 구문 검사를 실행한다.
- 실패한 테스트가 있으면 운영 배포를 승인하지 않는다.
- Vercel Preview에서 데스크톱과 390px 핵심 흐름을 검증한다.
- 운영 배포 후 최신 커밋 일치, 런타임 오류, 주요 API 상태를 확인한다.

## 10. 단계별 완료 기준

### 1단계 완료

- 비밀번호 원문이 브라우저 저장소와 API 응답에 존재하지 않는다.
- 중복 저장과 인증 무차별 대입이 차단된다.
- 기존 Redis 데이터와 고객 링크가 정상 작동한다.

### 2단계 완료

- 신규 직원이 별도 설명 없이 첫 화면에서 당일 우선 업무를 찾을 수 있다.
- 주요 편집 화면에서 이동·오류·새로고침으로 작성 내용이 사라지지 않는다.
- 모든 빈 상태와 오류 상태에 다음 행동이 있다.

### 3단계 완료

- 동일 역할의 버튼, 탭, 카드, 상태 표현이 전 화면에서 일관된다.
- 390px에서 핵심 흐름에 가로 넘침이나 가려진 행동이 없다.
- 모션 줄이기와 키보드 조작이 정상 작동한다.

### 4단계 완료

- 전체 테스트와 CI가 통과한다.
- 기능별 모듈 경계가 만들어져 한 기능 변경이 다른 기능 전역 상태를 직접 수정하지 않는다.
- 최신 운영 배포에서 런타임 오류가 없다.

## 11. 제외 범위

- 기존 고객 데이터 삭제 또는 일괄 변환
- 별도 모바일 앱 제작
- 유료 ERP, CRM 또는 외부 인증 서비스 도입
- 데모의 즉시 별도 프로젝트 이전
- 디자인 프레임워크 전체 교체
- 현재 요청과 무관한 신규 마케팅 기능 추가
